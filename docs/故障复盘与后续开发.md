## 一、一句话结论

本插件 `@local/study-assistant` 在 web profile 里是 **required 行**，所以它激活失败 = 整个 DSH 启动失败：

1. **根因 A（已修）**：宿主半边 `index.js` 的工具 schema 用了 `type: ['string','null']` 这类**类型数组**，
   `ctx.tools.register` 内部的 `assertSupportedJsonSchema` 直接抛错 → `dsh: startup failed: 1 required plugin did not activate`
   → 桌面端进安全模式。
2. **根因 B（未定位）**：改成"就地改 live 目录文件"后宿主半边能起来了，但**渲染进程**报
   `web boot: 1 entry did not activate / @local/study-assistant: failed` → 桌面端的 frontend plugin recovery
   在 23:47–23:50 之间把「正常模式 ↔ 安全模式」来回切了 7 次，最后放弃并**卸载插件**。

当前状态：插件**未安装**（备份齐全），桌面端未运行，环境无残留（见 §六）。

## 三、根因 A：宿主半边（已确认、已修）

`index.js` 的两个工具输出 schema 里写了类型数组：

```js
reason: { type: ['string', 'null'] }   // ✗
bytes:  { type: ['string', 'null'] }   // ✗
```

`ctx.tools.register` 内部调用 `assertSupportedJsonSchema`，只接受**单一类型字符串**：

```
JsonSchemaError: unsupported JSON schema:
  schema.properties.files.items.properties.reason.type must be a single type string
  (type arrays are not supported); …bytes.type …
    at assertSupportedJsonSchema (.../@deepseek-ai/dsh-tools/lib/index.js:326)
    at Proxy.register            (.../@deepseek-ai/dsh-tools/lib/index.js:2882)
    at Object.apply              (.../@local/study-assistant/index.js:175)

[harness-node] DSH entry failed: Error: dsh: startup failed: 1 required plugin did not activate
  study-assistant (required)
[desktop] Harness entry failed during startup; stopping immediately
[desktop] launch requested (safe mode)
```

**为什么这么致命**：本插件在 profile 里是 required 行 —— 一次工具注册失败就等价于整个 DSH 起不来，
而不是"这个功能不生效"。

**已修**：源码 `index.js`（23:44）与 live 件里都已无类型数组（只剩 `tests/host.test.js` 里的反例注释）。
**防护**：`tests/host.test.js` 内置了照抄官方规则的校验器（假 ctx 在注册时就抛），
`tools/verify-installed.mjs` 还会加载**生产版** `assertSupportedJsonSchema` 再校验一遍。
规则细节见 README 第九节第 4 条。

## 四、未决：根因 B —— 客户端半边为什么 `failed`

### 4.1 症状原文（桌面端日志）

```
[desktop] frontend plugin recovery 2026-09-29T15:47:09.040Z
[renderer] Error: web boot: 1 entry did not activate
[renderer] @local/study-assistant: failed
[desktop] plugin recovery detection: @local/study-assistant
```

四次全新页面加载（23:47 / 23:48 / 23:50:14 / 23:50:40）**错误完全一致**，即确定性问题，不是抖动。

### 4.2 这条信息的确切含义

web boot 内核在启动完所有 client entry 后汇总：

```js
if (s.fiber === void 0) → `${id}: import failed: …`          // bundle 加载/物化失败
else state = I7[fiber.state] → `${id}: pending/loading/active/failed/disposed/unloading`
```

我们拿到的是 `@local/study-assistant: failed`（**不是** `import failed`），
所以：**entry 存在、bundle 已加载，是插件激活期抛了错**（cordis 把该 fiber 置为 FAILED）。
（注意 effect 里抛错也会归到 owner fiber，所以"注册回调里抛"与"apply 直接抛"表现相同。）

### 4.3 已经排除的（离线真实注册表复现，两种顺序都跑了）

工具：`node tools/check-client-slots.mjs`（`--late` 走"槽位稍后声明"的真实顺序）。

| 检查项 | 结果 |
|---|---|
| `sidebar.panellist`（list/root，id=`study-assistant`） | ✓ 注册通过 |
| `main`（keyed/root，key=`study-assistant`） | ✓ 注册通过 |
| `conversation.composer.dock`（list/session，id=`study-due`） | ✓ 注册通过 |
| `sidebarRightTabs.register({id:'study-assistant/detail', kind:'studyDetail', priority:'extension'})` | ✓ 通过 |
| `sidebar.right.pane.tab`（keyed/session，key=`study-assistant/detail`） | ✓ 注册通过 |
| `sidebar.right.pane.tab.title`（keyed/session，同上 key） | ✓ 注册通过 |
| bundle 形态：`window.__ModuleLoader__.load({id, factory})`、只 `require('react')`、无顶层副作用 | ✓ 与官方模板 `templates/decoration/client.js` 一致 |
| `package.json` 的 `dsh.client`（`platform: 'web'` / `immediately: true` / `inject: []`） | ✓ 字段类型都合法；`inject` 是**客户端模块依赖**而非 cordis 服务，本 bundle 填 `[]` 正确 |
| `factory()` 物化（用桌面端真实 react） | ✓ 不抛 |

也就是说：**插件里那 6 处注册本身不是原因**（用的还是真实 `SlotCore` + 真实槽位 kind/scope 契约）。

### 4.4 剩余嫌疑

1. **bundle 加载/物化那一刻的环境问题**：客户端 bundle 是当 classic script 加载的
   （`document.createElement('script')` + `/plugins/??<id>/client.js&rev=…` 这种批量 URL），
   涉及 rev/缓存/批量拼接；若它其实走了 `import failed` 之外的另一条路径，需要现场证据。
2. **激活期 effect 抛错**：真实顺序下 `slots.inject` 的回调是稍后才跑的，若在**第二次声明**
   （重新挂载、会话切换）时撞内部状态（例如某槽位已被占），就会表现为 FAILED。
3. 其它：`Config` 解析、HMR/patch reload 与 generation 切换的交互。

### 4.5 为什么这次没抓到

桌面端持久化渲染进程证据时只保留**最后 50 行** console：

```js
const evidence = logs.slice(-50).join("\n").slice(-2e4).map(l => `[renderer] ${l}`)…
```

那次落盘的就是恢复页那几行（`HARNESS` / `Failed to load plugins` / `@local/study-assistant: failed`），
**cordis 打出的真实异常很可能就在这 50 行之前被挤掉了**，事后无法补。

### 4.6 抓错作业流程（下次一步到位）

1. 确认桌面端**未运行**（单实例锁），用带调试端口的方式启动，或启动后手动开 DevTools：

   ```powershell
   & "<DSH 安装目录>\DSH Desktop.exe" --remote-debugging-port=<调试端口>
   # 或启动后按 Ctrl+Shift+I；DevTools → Console 勾上 "Preserve log"
   ```

2. 通过 CDP 列出页面并抓 console（只读，不改宿主状态）：

   ```powershell
   (Invoke-RestMethod http://127.0.0.1:<调试端口>/json).webSocketDebuggerUrl
   ```

3. 安装插件（`plugin_manager` → `install_bundle`，target = 本目录），等页面完成一次 web boot。
4. 复制 Console 里**第一条**与 cordis / client 相关的错误（要完整堆栈，不要只截一行）。
5. 用 `node tools/check-client-slots.mjs --late` 对照：若脚本通过而线上仍 failed，
   说明问题在"加载/物化/时序"，而不在注册代码。
6. 把错误原文补进本节，再改代码。

> 在 §4.4 有结论之前，**不要重装**：装回去大概率会把 23:47–23:50 那套自愈循环再演一遍。

## 五、桌面端的自愈机制（后续开发必须知道）

| 触发 | 后果 |
|---|---|
| **宿主** required 行激活失败 | `dsh: startup failed: N required plugin did not activate` → 该 profile 不启动 → `[desktop] Harness entry failed during startup; stopping immediately` → **安全模式** |
| **渲染进程** web boot 失败 | `[desktop] frontend plugin recovery <时间>` + 把最后 50 行 renderer console 追加进 `harness.log` → 弹恢复页（`resources/plugin-recovery.html`），可强制进安全模式 |
| 失败反复出现 | **卸载插件**：写 `harness\recovery\plugin-removals.json`、备份到 `harness\recovery\plugin-removals\<removalId>\`、disable 该 generation、冷启动时 sweep、最后记 `boot-verified removal` |
| 安全模式 | 第三方 web profile bundle **全部被屏蔽**（本插件随之不加载）；`pnpm` 不可用 → `install_bundle` 会失败（`'pnpm' 不是内部或外部命令`） |
| 端口与写句柄 | 首选 `127.0.0.1:<端口>`，被占则用临时端口；**旧/孤儿 harness 会握住会话写句柄** → `session … is already owned by an active write handle`（本次就是它让会话打不开） |

**结论性教训**：对 required 行的插件，"**能启动**"本身就是一条必须验证的契约。
开发期更稳的做法是：先用非 required 行（或先只装客户端半边）验证，再升级成 required。

## 十、排障速查命令

```powershell

# 2. 捞关键事件

  -Pattern 'startup failed|plugin failures|web boot|frontend plugin recovery|plugin recovery detection|boot-verified'

# 3. 谁占着首选端口（孤儿 harness 在这里现形）
netstat -ano | Select-String '<首选端口>'
```
